# خطة مقترحة لتطوير وتكامل تطبيق عمران للألعاب

**الحالة:** مسودة للموافقة قبل التنفيذ

**تاريخ التدقيق:** 26 أغسطس 2026

**نطاق الخطة:** تطوير `omran-store` مع الحفاظ على جميع الصفحات والمسارات والخيارات والمميزات الحالية، وعدم تحويل الموقع إلى متجر دفع مباشر إلا بقرار مستقل لاحق.

## 1. النتيجة التي سيحدثها التطوير

الهدف المقترح هو تحويل الموقع من كتالوج ثابت جيد العرض إلى **قناة مبيعات موثوقة وقابلة للقياس والإدارة**. سيظل المستخدم قادراً على تصفح الأقسام والبحث والفلترة وفتح المعاينة السريعة وصفحة المنتج ومشاركة المنتج والاستفسار عبر واتساب، لكن كل خطوة ستصبح أدق وأسهل في القياس. وستصبح بيانات المنتجات وإعدادات النشاط ومزامنة إنستغرام محكومة بعقود تحقق واضحة، مع مسار اختياري لاحق لاستقبال الاستفسارات وإدارتها مركزياً دون كشف أي أسرار في المتصفح.

المقصود ليس إعادة بناء التطبيق من الصفر، ولا إزالة مكونات السلة القديمة أو عقود الاختبارات، ولا تغيير نموذج «كتالوج + واتساب». المقصود هو إضافة طبقات حماية وقياس وتكامل حول النظام الحالي تدريجياً، بحيث يكون كل إصدار قابلاً للاختبار والرجوع إلى الإصدار السابق.

## 2. نتيجة التدقيق الحالية

المشروع مبني بـ **Next.js App Router وTypeScript وReact وTailwind CSS**، ويستخدم تصديراً ثابتاً على GitHub Pages وبناء Next.js عادي على Vercel. يحتوي المستودع على 15 مساراً، و20 مكوّناً، و12 منتجاً فعلياً، وصفحات ثابتة للمعلومات القانونية والتواصل، وصفحات تفاصيل المنتجات، وبيانات منظمة للـ SEO، وزر واتساب، وخلاصة إنستغرام تتم مزامنتها آلياً كل ست ساعات.

خط الأساس الحالي جيد وظيفياً: نجحت الاختبارات وعددها 21، ونجح فحص TypeScript، ونجح ESLint دون أخطاء، ونجح بناء الإنتاج. ظهر تحذير واحد غير مانع في `InstagramFeed.tsx` بسبب استخدام `<img>` بدلاً من مكوّن الصور المناسب. كما أن النسخة المنشورة متاحة على Vercel، بينما يعيد النطاق الجذري التوجيه إلى نسخة `www`.

| المجال | الوضع الحالي | ما يجب الحفاظ عليه | الأولوية |
|---|---|---|---|
| الواجهة | RTL عربي، Header، Hero، الأقسام، الكتالوج، FAQ، التواصل، Footer | كل الأقسام والتخطيط وروابط التنقل | عالية جداً |
| الكتالوج | 12 منتجاً، بحث، فلترة، ترتيب، معاينة، صفحات تفاصيل | كل المنتجات و`slug` وSKU والصور والشارات | عالية جداً |
| التحويل | روابط Click-to-WhatsApp، بلا دفع مباشر | عمل الروابط الحالية كخطة بديلة دائمة | عالية جداً |

## 3. المخاطر التي يجب معالجتها قبل التوسع

يوجد حالياً **أربع نتائج عالية الخطورة** في `npm audit --omit=dev`: نسخة متأثرة من `nanoid`، ونسخة PostCSS متداخلة مع Next.js، ومشكلات أمنية مرتبطة بـ `sharp`. لا ينبغي تنفيذ ترقية عشوائية مباشرة على الفرع الرئيسي؛ يجب تحديث الاعتمادات وملف القفل في دفعة مستقلة، ثم إعادة الاختبارات والبناء ومراجعة الصور.

سير العمل الخاص بـ Vercel يشغّل `verify:release`، بينما سير عمل GitHub Pages يشغّل `next build` فقط. هذا يجعل بوابة الجودة غير متناظرة بين بيئتي النشر. يجب توحيد البوابة قبل أي إضافة كبيرة حتى لا يمر كود إلى Pages دون اختبارات المشروع.

بيانات النشاط التجاري والروابط والرقم والإعدادات التشغيلية ما زالت hard-coded في `src/lib/site.ts`. هذا مناسب لعدد صغير من التغييرات، لكنه يرفع احتمال الخطأ عند تحديث رقم واتساب أو عنوان فرع أو نص إعلان. الحل الآمن ليس نقل كل شيء إلى قاعدة بيانات فوراً، بل البدء بعقد إعدادات موحّد والتحقق الآلي من القيم، ثم اتخاذ قرار مستقل حول لوحة الإدارة.

مزامنة إنستغرام الحالية تحفظ نتيجة الطلب مباشرة في `src/data/instagram-feed.json` ثم تدفع commit إلى `main` وتطلق النشر. يلزم منع الكتابة عند عودة قائمة فارغة غير متوقعة، حفظ آخر نسخة سليمة، التحقق من شكل البيانات قبل commit، وتسجيل سبب الفشل دون كشف التوكن. إذا توسع التكامل إلى استقبال الرسائل أو التعليقات فسيحتاج إلى endpoint خادم؛ GitHub Pages وحده لا يستطيع استقبال webhook.

المعاينة الحية أعادت في صفحة المنتج عنوان HTML عاماً بدلاً من العنوان الخاص بالمنتج، بالرغم من وجود `generateMetadata` في المصدر. هذه ملاحظة يجب إعادة التحقق منها بعد نشر جديد قبل اعتبارها خللاً نهائياً، لكنها تستحق اختباراً آلياً يمنع تكرارها. كما أن بعض رسائل واتساب تستخدم رابط `/products` العام بدلاً من رابط slug المنتج، ما يضعف دقة التتبع وتجربة العودة إلى المنتج.

## 4. بدائل التكامل الممكنة

بما أن التطبيق الحالي ثابت في جزء من النشر ولا يحتوي على خادم أو قاعدة بيانات، فهناك مساران صحيحان. لا ينبغي اختيار المسار الأثقل قبل معرفة ما إذا كانت الحاجة الحقيقية هي القياس فقط أم إدارة الاستفسارات والرسائل مركزياً.

| النهج | المفاضلات | التكلفة | تعقيد الإعداد |
|---|---|---|---|
| **المسار المحافظ: تحسين الموقع الحالي فقط** | يحافظ على GitHub Pages وVercel، ويضيف التحقق، الروابط الدقيقة، قياس نقرات واتساب، ومزامنة Instagram أكثر أماناً. لا يوفر صندوق وارد أو قاعدة بيانات للعملاء. | منخفضة؛ غالباً ضمن الخدمات الحالية، مع احتمال تكلفة خطة التحليلات بحسب حساب Vercel | منخفض إلى متوسط |
| **مسار تشغيلي: طبقة خادم وإدارة آمنة** | يضيف قاعدة بيانات ولوحة إدارة للمنتجات والإعدادات وسجل استفسارات، ويجعل Vercel المنصة الأساسية للوظائف الخادمية مع إبقاء Pages نسخة ثابتة احتياطية. يحتاج حماية دخول، نسخاً احتياطية، وسياسة خصوصية وتشغيلاً مستمراً. | متوسطة؛ قد توجد تكلفة استضافة/قاعدة بيانات ورسوم مزود الرسائل | متوسط إلى عالٍ |
| **تكامل Meta كامل لاحقاً** | يضيف WhatsApp Cloud API لاستقبال الرسائل والحالات، وربما Instagram Webhooks للتعليقات والرسائل. يحقق أتمتة حقيقية لكنه يحتاج Meta App، حساباً احترافياً، أسراراً دائمة، تحققاً من webhooks، إزالة التكرار، ومراجعات/صلاحيات عند الحاجة. | متوسطة إلى مرتفعة بحسب الرسائل ومزود البنية | عالٍ |

التوصية الهندسية المحافظة هي تنفيذ الدفعات الأولى المشتركة بين المسارات، ثم اتخاذ قرار مستقل بعد ظهور بيانات النقرات وحجم الاستفسارات. لا يلزم إدخال WhatsApp Cloud API لمجرد أن الموقع يستخدم روابط واتساب؛ الروابط الحالية أقل تعقيداً وتحافظ على fallback واضح. أما إذا كان المطلوب هو **تسجيل كل استفسار وتوزيعه ومتابعة حالته**، فحينها يصبح التكامل الخادمي منطقياً.

## 5. خطة التنفيذ على دفعات

### الدفعة 0 — تثبيت خط الأساس والحماية قبل التغيير

لن يتغير سلوك المستخدم في هذه الدفعة. سيتم إنشاء فرع عمل مستقل، وتسجيل حالة المستودع، وأخذ نسخة من ملفات JSON والأصول، وتوثيق قائمة المسارات الحالية. ستُضاف اختبارات تمنع حذف المسارات أو تغيير أسماء المنتجات وslug وSKU دون تصريح. كما سيتم جعل `verify:release` بوابة مشتركة في Vercel وGitHub Pages، مع إبقاء `main` محمياً وعدم الدفع إليه من سكربتات المزامنة إلا عند اجتياز التحقق.

**معيار القبول:** نفس المسارات الحالية تعمل، و21 اختباراً على الأقل تنجح، وTypeScript وESLint والبناء ينجحون على بيئتي النشر، ولا يتغير شكل الصفحة أو سلوك زر واتساب.

**خطة التراجع:** إلغاء الفرع أو إعادة النشر من tag خط الأساس دون أي migration أو حذف بيانات.

### الدفعة 1 — التصحيح الأمني واستقرار النشر

سيتم تحديث الاعتمادات المتأثرة أمنياً إلى نسخ مصححة ومتوافقة، مع مراجعة `package-lock.json`، وإعادة اختبار الصور والبناء على Node 20. لن يُستخدم `npm audit fix` بشكل أعمى؛ ستُراجع كل ترقية لأنها قد تغير سلوك Next.js أو التحسينات المحلية للصور.

سيتم أيضاً توحيد سياسة النطاق بين `omrantoys.store` و`www.omrantoys.store`: اختيار نطاق أساسي واحد، ضبط `siteConfig.url`، والتحقق من canonical وOpen Graph وJSON-LD وخريطة الموقع. كما سيتم إصلاح أو اختبار metadata الخاصة بصفحات المنتجات، وجعل روابط واتساب للمنتج تستخدم slug المنتج الفعلي حيث يلزم.

**معيار القبول:** لا توجد ثغرات عالية في فحص الاعتمادات المستهدف، وتظهر metadata الخاصة بصفحة المنتج في HTML المبني، ولا توجد روابط منتج تشير إلى صفحة عامة عندما يكون slug معروفاً، وتظل كل المسارات الحالية صالحة.

**خطة التراجع:** الاحتفاظ بملف القفل السابق ونسخة tag؛ إذا فشلت ترقية، تُستعاد الحزمة المتأثرة وحدها ولا تُلغى تحسينات الدفعات الأخرى.

### الدفعة 2 — قياس التحويل دون جمع بيانات شخصية

سيتم وضع قاموس أحداث موحّد، مثل: مشاهدة منتج، فتح معاينة سريعة، استخدام البحث، تغيير القسم، فتح واتساب من بطاقة، فتح واتساب من صفحة المنتج، ومتابعة رابط إنستغرام. ستُرسل الأحداث بأسماء ثابتة وبيانات غير حساسة مثل SKU أو القسم أو موضع الزر، دون إرسال اسم العميل أو رقم الهاتف أو نص المحادثة.

تدعم Vercel Web Analytics دالة `track()` للأحداث المخصصة في تطبيقات Next.js، مع قيود على حجم وعمق البيانات المرسلة.[4] سيُستخدم ذلك فقط لقياس القنوات والمواضع، ولن يُعتبر بديلاً عن قياس إتمام المحادثة داخل واتساب؛ فالضغط على الرابط يمكن قياسه، أما نتيجة المحادثة فتحتاج نظاماً خارجياً أو وسم مصدر واضح.

**معيار القبول:** كل حدث يعمل على الهاتف وسطح المكتب، ولا يكسر فتح واتساب عند فشل التحليلات، ولا يحتوي payload على بيانات شخصية، ويمكن رؤية الأحداث في لوحة التحليلات أو تسجيل سبب عدم توفرها.

**خطة التراجع:** تعطيل الأحداث خلف دالة واحدة أو feature flag دون إزالة أزرار الموقع أو تغيير روابطها.

### الدفعة 3 — جعل المحتوى قابلاً للتحقق والتحديث الآمن

سيتم تعريف schema واضحة للمنتجات والأقسام والإعدادات وخلاصة إنستغرام، مع فحص آلي للـ slug وSKU ومسارات الصور وتكرار المعرفات وصحة الروابط. ستظل البيانات في شكل متوافق مع الوضع الحالي في البداية؛ الهدف هو منع إدخال بيانات ناقصة أو كسر build، لا فرض قاعدة بيانات فوراً.

سيتم تحسين سكربت Instagram بحيث يكتب ملفاً مؤقتاً، يتحقق من بنيته، ويرفض استبدال آخر feed سليمة بقائمة فارغة أو استجابة غير مكتملة. ستبقى الصفحة قادرة على عرض fallback آمن. كما ستُقلص صلاحيات workflow قدر الإمكان، ويُفصل تحديث المحتوى عن النشر إن كان ذلك متاحاً دون تعقيد زائد.

**معيار القبول:** فشل Meta أو انتهاء التوكن لا يحذف آخر feed سليمة، وتظهر رسالة فشل مفيدة في سجل workflow دون كشف الأسرار، وملف feed صالح يمر بفحص schema قبل أي نشر.

**خطة التراجع:** إعادة آخر ملف feed سليم وإعادة تشغيل build، دون تعديل واجهة الكتالوج أو بيانات المنتجات.

### الدفعة 4 — طبقة إدارة المحتوى، بقرار مستقل

إذا كان عدد المنتجات والتحديثات سيبقى صغيراً، يكفي مسار مراجعة GitHub مع ملفات بيانات متحققة. إذا كان المطلوب أن يضيف غير المطورين المنتجات ويعدّلوا الأسعار والتوفر والفروع والإعلانات، فسيتم تصميم لوحة إدارة محمية، مع قاعدة بيانات ونسخ احتياطية وسجل تغييرات وصلاحيات منفصلة. ستُبنى القراءة أولاً من المصدر الجديد مع fallback للبيانات الحالية، ثم تتم الكتابة بعد تحقق المستخدم، بدلاً من حذف الملفات الحالية دفعة واحدة.

لن تُضاف لوحة عامة أو endpoint كتابة مكشوف. وسيكون الوصول الإداري محمياً بالمصادقة، وتُحفظ الأسرار في بيئة الخادم فقط. إذا ظهر احتياج مستقبلي إلى شراء ودفع مباشر، فسيكون ذلك مشروعاً منفصلاً يُقيّم تكامل تجارة مُدار مثل Shopify بدلاً من بناء الدفع يدوياً، مع بقاء نموذج الكتالوج الحالي سليماً حتى اتخاذ القرار.

**معيار القبول:** يستطيع المشرف المصرح له تعديل محتوى محدد، وتظهر التغييرات بعد تحقق آلي، ويوجد سجل ونسخة تراجع، ولا تتأثر الصفحات العامة عند فشل لوحة الإدارة.

### الدفعة 5 — تكامل واتساب وMeta عند ثبوت الحاجة التشغيلية

إذا أثبتت البيانات أن الحاجة هي إدارة المحادثات لا مجرد قياس النقرات، يُضاف WhatsApp Cloud API خلف خادم Vercel أو خدمة خادمية مناسبة. توضح وثائق Meta الرسمية أن Cloud API يدعم إرسال الرسائل واستقبال webhooks، وأن الوصول الإنتاجي يحتاج توكن نظام محفوظاً بأمان وإعدادات حساب WhatsApp Business.[1] كما أن webhooks قد تُعاد عند الفشل لمدة تصل إلى سبعة أيام، لذلك يجب تطبيق التحقق من التوقيع، والاستجابة السريعة، وتخزين event IDs لمنع التكرار.[2]

سيبقى رابط `wa.me` الحالي هو fallback إذا تعذر الخادم أو لم يكن الحساب جاهزاً. لن يوضع access token في `NEXT_PUBLIC_*` أو في JavaScript العميل. ستُخزن الرسائل الضرورية فقط، مع سياسة احتفاظ وحذف واضحة، ولن تُبنى أتمتة إرسال جماعي قبل التأكد من موافقات وقوالب Meta المناسبة.

أما Instagram Webhooks فستكون مرحلة لاحقة اختيارية. الوثائق الرسمية الحالية تتطلب endpoint HTTPS، تحققاً من طلب الاشتراك، والتحقق من توقيع `X-Hub-Signature-256`، كما تتطلب حساب Instagram احترافياً وإعدادات وصلاحيات Meta مناسبة.[3] لذلك لا أوصي بتحويل مزامنة الخلاصة الحالية إلى webhook قبل وجود حاجة فعلية للتعليقات أو الرسائل؛ المزامنة الدورية المحسنة أبسط وأقل خطراً لخلاصة العرض.

**معيار القبول:** استقبال webhook والتحقق منه وإزالة تكراره، حفظ الحد الأدنى من البيانات، وجود شاشة خطأ/fallback، واختبار يدوي على حساب Meta تجريبي قبل الإنتاج.

### الدفعة 6 — اختبار شامل وإطلاق تدريجي

سيتم إضافة اختبارات smoke للصفحة الرئيسية والكتالوج وصفحة المنتج والصفحات القانونية والروابط الخارجية، واختبار 404، واختبار الهاتف وRTL، واختبار HTML للـ metadata والـ JSON-LD. ستتم معاينة build على Vercel قبل الإنتاج، ثم نشر تدريجي، ثم فحص النطاق الأساسي والـ sitemap والـ robots والـ canonical بعد النشر.

سيتم إنشاء تقرير release لكل دفعة يتضمن commit، نتائج الاختبارات، قائمة المسارات، صوراً أو لقطات للمسارات الحرجة، وقرار الإطلاق أو التراجع. لا تُعتبر الدفعة مكتملة بمجرد نجاح build؛ يجب التأكد من أن البحث والفلاتر والـ WhatsApp والمعاينة وصفحة المنتج وخلاصة Instagram ما زالت تعمل.

## 6. قواعد عدم كسر النظام

لن يتم الحذف المباشر لأي مكوّن أو ملف legacy. إذا ثبت عدم استخدام مكوّن، سيبقى أولاً خلف توافق واختبارات، ثم يحتاج حذفه إلى دفعة منفصلة وموافقة صريحة. لن تتغير عقود `Product` أو `ProductImage` أو `CategoryId` أو مسارات `/products/[slug]` دون migration توافقية واختبارات.

لن تُعدّل `main` مباشرة. كل دفعة ستكون في فرع مستقل، ثم تمر ببوابة التحقق. ستُحفظ نسخة من آخر إصدار منشور وملفات المحتوى، ويجب أن يكون التراجع إعادة نشر commit سابقاً لا إصلاحاً يدوياً في الإنتاج.

لن تُستخدم feature flags لإخفاء أخطاء البيانات أو تجاوز الاختبارات. ستُستخدم فقط لتشغيل التكامل الجديد اختيارياً مع بقاء المسار القديم متاحاً. أي تكامل خارجي يجب أن يفشل بشكل لطيف: يبقى الكتالوج مرئياً، وتبقى روابط واتساب الأساسية متاحة، ولا تُستبدل بيانات صحيحة ببيانات فارغة.

## 7. ما أحتاجه منك للموافقة

أحتاج موافقتك على **بدء الدفعات 0 و1 و2 و3 فقط** باعتبارها مرحلة حماية وتحسين لا تغيّر نموذج الموقع. بعد إتمامها وتقديم نتائج القياس، نقرر منفصلاً بين إبقاء الإدارة عبر GitHub أو بناء لوحة إدارة، ثم نقرر إن كان WhatsApp Cloud API ضرورياً.

كما أحتاج منك تأكيد اختيار النطاق التشغيلي للمرحلة التالية:

1. **مسار محافظ:** نكتفي بتحصين الموقع وقياس النقرات وتحسين مزامنة Instagram، مع بقاء الاستفسارات داخل واتساب يدوياً.
2. **مسار تشغيلي موسع:** نكمل لاحقاً إلى لوحة إدارة وسجل استفسارات وتكامل WhatsApp Cloud API، مع جعل Vercel المنصة الأساسية للوظائف الخادمية وترك GitHub Pages نسخة ثابتة احتياطية.

إذا وافقت، سأبدأ بالدفعة 0 في فرع مستقل، وأتوقف عند أي تغيير يقترب من سلوك المستخدم أو بنية البيانات حتى يُراجع ويجتاز اختبارات التراجع.
