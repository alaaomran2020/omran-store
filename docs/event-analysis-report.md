# تقرير الأحداث وقرار التكاملات

**التاريخ:** 26 أغسطس 2026

## نطاق القياس الحالي

تسجل طبقة القياس أحداثاً مجهّلة وغير حرجة لتجربة الكتالوج. لا ترسل الطبقة أسماء العملاء أو أرقام الهواتف أو محتوى محادثات واتساب، كما أن فشل خدمة القياس لا يمنع فتح الرابط أو استخدام الميزة الأساسية.

| الحدث | الحقول التشغيلية | ما الذي يقيسه |
|---|---|---|
| `catalog_search` | `queryLength`, `resultCount`, `source` | استخدام البحث ووجود نتائج |
| `catalog_filter` | `filter`, `value` | الاهتمام بالترتيب أو قسم محدد |
| `product_quick_view` | `sku`, `category`, `source` | المنتجات التي تستدعي معاينة سريعة |
| `whatsapp_inquiry` | `sku`, `category`, `source`, `mode` | نية بدء استفسار عام أو عن منتج |
| `product_share` | `sku`, `source` | المنتجات التي يتم تداولها |
| `product_favorite` | `sku`, `added` | التفاعل المحلي مع المفضلة |

## نتيجة الوصول إلى البيانات

تم تحديد مشروع Vercel المرتبط بالمستودع ومحاولة قراءة Custom Events للأيام الثلاثين الأخيرة باستعلام read-only. رفضت Vercel الاستعلام بحالة `402 Payment Required` لأن قراءة الأحداث المخصصة مقيدة بخطة Enterprise أو Pro. لذلك لا يجوز اعتبار أي معدل تحويل أو ترتيب منتجات مثبتاً من بيانات حية حتى الآن.

المتاح حالياً هو **قاموس أحداث صالح للتحليل عند توفر تصدير**، وليس أرقام أداء. لا توجد حاجة لإضافة خادم أو قاعدة بيانات فقط لتجاوز غياب صلاحية القراءة، لأن ذلك سيزيد سطح المخاطر قبل إثبات الحاجة.

## قرار لوحة الإدارة

التوصية الحالية هي التأجيل. مصدر الحقيقة ما زال ملف المنتجات في Git، وعدد المنتجات 12، وتغيير الكتالوج لا يثبت بعد وجود عنق زجاجة تشغيلي يستلزم لوحة إدارة. يعاد تقييم القرار إذا ظهرت خلال 14–30 يوماً مؤشرات مثل تكرار تحديثات يومية من أكثر من محرر، أخطاء متكررة في بنية JSON، أو تأخر واضح في تحديث المنتجات بسبب الاعتماد على النشر البرمجي.

## قرار WhatsApp Cloud API

التوصية الحالية هي التأجيل والإبقاء على روابط `wa.me`. تكامل Cloud API لا يصبح مبرراً بمجرد ارتفاع النقرات؛ يلزم إثبات حاجة تشغيلية مثل توزيع المحادثات على أكثر من موظف، سجل حالات للاستفسارات، قوالب ورسائل آلية، webhooks، أو ربط الطلبات بمخزون فعلي. نقرات واتساب الحالية تقيس نية التواصل ولا تقيس وصول الرسالة أو إتمام البيع، لذلك لا تكفي وحدها لتبرير تكامل خادمي.

## طريقة القرار بعد توفر تصدير الأحداث

يجب تحليل البيانات حسب اسم الحدث، مصدره، SKU، القسم، ونوع الجهاز، مع مقارنة `whatsapp_inquiry` بعدد زيارات صفحات المنتجات. ويُستحسن تقسيم النتائج إلى 14 يوماً ثم 30 يوماً لتجنب قرار مبني على يوم واحد أو حملة مؤقتة.

| النتيجة | الإجراء المقترح |
|---|---|
| أحداث قليلة أو غير مستقرة | الإبقاء على الكتالوج الثابت والقياس الحالي |
| نقرات كثيرة لكن بلا دليل على عبء تشغيلي | تحسين الرسائل والـ CTA، دون Cloud API |
| تحديثات كتالوج متكررة من عدة محررين | بناء لوحة إدارة صغيرة بصلاحيات وتدقيق وتراجع |
| محادثات كثيرة تحتاج توزيعاً وحالات وwebhooks | دراسة WhatsApp Cloud API في مشروع منفصل مع أسرار server-side |

## الخلاصة

تم تنفيذ الجزء الآمن من الخيار الثاني: تثبيت قاموس الأحداث وتجهيز منهج التحليل. القرار المسؤول حالياً هو عدم إدخال لوحة إدارة أو WhatsApp Cloud API قبل توفر بيانات أحداث قابلة للقراءة أو ظهور احتياج تشغيلي واضح. هذا يحافظ على بساطة التطبيق الحالي ويمنع إضافة خادم وأسرار ونقاط فشل لا يحتاجها المنتج بعد.
